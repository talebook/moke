# Moke 扩展信任模型

## 目标与威胁边界

Moke 将本地 ZIP、Talebook 服务器、本机网页及扩展声明视为不可信，使用签名、内容绑定确认与权限快照防止未批准内容通过正常安装/启用链路执行。

原生后端以当前用户权限运行，不是沙箱。同用户恶意进程若能任意写 AppData 或操纵进程，仍可在最后一次验证与 OS loader 打开文件之间替换代码和依赖；目录权限、重复哈希和原子替换不能彻底消除该竞态。完整格式、安装事务、迁移说明和保障边界见 [ZIP 扩展安装与迁移](extension-zip.md)。

## 包签名

扩展在 `manifest.json` 中声明稳定身份和分发来源：

```json
{
  "publisher": {
    "id": "org.example",
    "name": "Example Publisher",
    "source": "https://example.org/moke/extensions/example"
  }
}
```

发布者使用 Ed25519 对以下内容签名：扩展名、版本、发布者 ID、来源、`key_id` 和整个包的 SHA-256 摘要。`signature.json` 是分离签名，不进入自身摘要。宿主生成、运行期可变或不会安装的根目录文件 `signature.json`、`storage.json`、`uninstall.exe`、`installer.nsi`、`*-setup.exe` 不进入摘要，且不能被声明为后端入口；Moke 不执行扩展提供的 `uninstall.exe`。包内符号链接会被拒绝。

构建和签名流程：

```bash
openssl genpkey -algorithm Ed25519 -out ../publisher.pem
moke-ext build
moke-ext sign --key ../publisher.pem --key-id release-2026
moke-ext package
```

私钥必须放在包外并由发布者的发布系统保护。`moke-ext sign` 会拒绝位于 `dist/` 内的私钥。

## 激活门禁与权限变更

Moke 在首次启用以及每次应用启动时重新计算包摘要和签名状态。扩展管理页展示签名状态、发布者、来源、密钥 ID、内容摘要和权限 diff。

- 签名无效、同版本内容变化、版本降级/重放、已撤销密钥：直接阻断。
- 未签名且包含原生后端：直接阻断，防止执行任意二进制。
- 未签名的旧版纯 UI/无头扩展：允许高风险确认，但确认仅绑定当前摘要。
- 签名有效但发布者或轮换密钥未知：每次启用都必须高风险确认，且不会跨 Moke 重启自动恢复。
- 首次启用、版本升级、来源/发布者变化、权限扩大：必须重新确认。
- 内容、版本、来源和权限均未变化：可以使用既有授权恢复启用。

确认记录存放于扩展根目录旁的宿主 `trust.json`，不包含秘密。它绑定完整内容摘要、版本、发布者、来源和权限集合，因此一次点击不会永久绕过后续变化。发布者信任锚只允许编译进已签名的 Moke 二进制；可写的 AppData 记录不会把未知密钥提升为官方信任，防止同一用户权限下的本机进程伪造 `trust.json` 后安排下次启动执行。

运行期间 API 只使用启用时确认的权限快照，不再从可变的磁盘 manifest 动态读取权限。修改 manifest 不会扩大正在运行的扩展权限；重启后门禁会使它保持禁用。

## 发布者密钥轮换与撤销

轮换时保持 `publisher.id` 和 `publisher.source` 不变，使用新的 `key_id` 和 Ed25519 密钥重新签名并提升扩展版本。Moke 显示轮换风险并要求重新确认。官方密钥只有在 Moke 发布版同时内置新公钥锚点后才会获得可持久恢复的信任；未知密钥的用户确认只对当前启用会话有效。

发现密钥泄露时：

1. 立即禁用或卸载受影响扩展；
2. 在下一版 Moke 的 `REVOKED_KEYS` 紧急拒绝列表加入发布者 ID 和密钥 ID；
3. 使用新密钥、版本和 `key_id` 发布替代包；
4. 用户需要对新密钥和新包重新确认。

官方发布根密钥的离线保管、内置锚点和联网撤销清单属于发布基础设施，不应把私钥提交到本仓库。未内置锚点前，有效签名仍按“未知发布者”高风险确认，不会被伪装成官方受信任状态。

## Token 生命周期与兼容

扩展 API token 是随机、按启用会话分配的 bearer capability：

- token 只保存在 Moke 和扩展后端进程内存中，不写入 `runtime.json`；
- 每次重新启用和每次 Moke 启动都会自动轮换；
- 旧版 `runtime.json` 中已有的 token 在首次恢复时被忽略并清除；
- 禁用扩展会立即从认证映射删除 token；
- token 只能访问该次启用时确认的权限集合。

旧扩展无需修改请求头格式，但不能依赖 token 跨 Moke 重启保持不变。原生后端继续从 `MOKE_EXT_TOKEN` 环境变量读取当前会话 token。

## 当前兼容策略

旧版未签名原生扩展不再自动运行；发布者必须增加 `publisher`、提升版本并生成 `signature.json`。旧版未签名纯 UI/无头扩展可按当前摘要逐包确认，以便渐进迁移。任何权限或来源变化都会再次触发确认。

ZIP 是推荐分发格式；NSIS 扩展安装器已退出 CLI 推荐流程。新增强制权限及 403 迁移映射见 [ZIP 文档](extension-zip.md#旧权限与连接兼容)。
